# PRD: 팀 프로젝트를 위한 팀 편성 웹 앱

- 과목: 데이터프로젝트 (중간고사 대체과제)
- 근거 자료: 「중간 과제 공고: 팀 프로젝트를 위한 팀을 편성하는 웹 앱 만들기」(이하 "공고"), 시연 동영상
- 상태: 초안 (사용자 검토 대기)

## 1. 목적과 성공 기준

### 1.1 목적
학생들이 팀 프로젝트를 위한 팀을 스스로 편성하는 웹 앱을 만든다. 학생은 팀에 지원하고 팀원은 투표로 받아들이며, 관리자(교수)가 모집을 마감하면 팀이 없는 학생을 AI가 배정하고 앱이 그 배정을 규칙으로 검사한다.

### 1.2 성공 기준
1. 공개하지 않은 채점 시나리오 3개(쉬움·중간·어려움)를 자동 채점 프로그램이 끝까지 실행할 수 있다.
   - 화면 요소마다 공고 2.7절의 Streamlit `key`가 정확히 붙어 있다.
   - 단계마다 결과 안내(`result`)의 첫 단어(승인·대기·거절·막힘)가 기대 결과와 같다.
2. 확정한 팀 구성이 모든 규칙(2.3절)을 지킨다.
3. 공고 6.3절의 감점 사유에 하나도 해당하지 않는다.
4. 시나리오 밖 점수 항목(PRD·구현 계획, README 사례, 키 관리, DB 유일성 제약, DB 일시정지 막기)을 모두 갖춘다.

### 1.3 채점 시나리오의 범위 (공고 6.2절)
- 학생 수 8~16명, 팀 수 3~4개. 학생의 이름·역할, 지원과 투표의 순서는 연습용 시나리오와 다를 수 있다.
- 모집 마감 때 AI 배정을 받아야 하는 학생은 8명 이하이다.
- 따라서 앱은 학생 이름, 학번, 지원 순서를 보고 결과를 정하지 않는다. 모든 판단은 역할과 규칙으로만 한다(감점 19번: 연습용 시나리오에 맞춰 결과를 미리 정해 둔 코드는 그 시나리오 0점).

## 2. 사용자

| 사용자 | 로그인 | 하는 일 |
|---|---|---|
| 학생(가상 학생) | 명단 CSV의 학번, 비밀번호 `1234` | 팀 목록과 팀원 보기, 팀에 지원, 내 팀에 들어온 지원에 찬성·거부 |
| 관리자(교수) | 학번 `admin`, 비밀번호는 비밀 값 `ADMIN_PASSWORD` | 명단을 올려 처음 상태 만들기, 모집 마감, AI 배정 받아 확인하고 확정 |

- 화면을 조작하는 사람(과제할 때는 수강생, 채점할 때는 채점자)이 가상 학생과 관리자로 번갈아 로그인한다.
- 관리자 계정은 앱이 시작할 때 `ADMIN_PASSWORD`로 만들거나 비밀번호를 갱신한다. 명단을 다시 올려도 관리자 계정은 남는다.

## 3. 용어

- 역할 6개: 기획자, 웹 프로그래머, 프론트엔드 디자이너, 테스터, 보고서 작성자, 발표자. 약자는 PL, WP, FD, TT, RW, PT.
- 주 역할: 학생마다 1개. 팀 안의 중복을 따질 때 쓴다.
- 보조 역할: 학생마다 0~2개. 필수 포함 역할을 맡을 수 있는지 따질 때만 쓴다.
- 필수 포함 역할: 기획자와 웹 프로그래머. 확정한 팀마다 각각을 맡을 학생이 서로 다른 사람으로 1명씩 있어야 한다.
- 맡을 수 있다: 그 역할이 학생의 주 역할이거나 보조 역할이다.
- 승인: 지원이 받아들여져 지원자가 팀원이 됨.
- 대기: 지원이 접수되어 팀원의 투표를 기다림.
- 거절: 접수된 지원이 팀원의 거부, 승인 직전 검사, 모집 마감으로 떨어짐.
- 막힘: 지원을 아예 접수하지 않음(DB에 기록하지 않음).

## 4. 규칙

### 4.1 팀 규칙 (공고 2.3절)
1. 팀 수는 관리자가 명단을 올릴 때 정한다. 팀 이름은 팀1, 팀2, …이다.
2. 마감 뒤 확정한 팀 구성에서 모든 팀은 2~4명이다(빈 팀 없음).
3. 주 역할이 같은 학생이 한 팀에 2명 이상이면 안 된다.
4. 확정한 팀마다 기획자를 맡을 학생과 웹 프로그래머를 맡을 학생이 서로 다른 사람으로 1명씩 있다.

### 4.2 지원 (공고 2.4절)
지원 단추를 누르면 아래 순서로 검사한다. 하나라도 걸리면 "막힘"이고, DB에 아무것도 기록하지 않는다.

| 순서 | 검사 | 막힘 안내 |
|---|---|---|
| 1 | 모집이 마감됨 | 막힘: 모집이 마감됨 |
| 2 | 지원자가 이미 팀에 있음 | 막힘: 이미 팀이 있음 |
| 3 | 지원자에게 결과를 기다리는 지원이 있음 | 막힘: 결과를 기다리는 지원이 있음 |
| 4 | 팀이 4명으로 꽉 참 | 막힘: 팀이 꽉 참 |
| 5 | 지원자와 주 역할이 같은 팀원이 있음 | 막힘: 같은 주 역할의 팀원이 있음 |
| 6 | 필수 포함 역할 자리가 모자람(4.4절) | 막힘: 필수 포함 역할 자리가 모자람 (남는 자리 n개, 채워야 할 역할: …) |

검사를 통과하면:
- 빈 팀이면 바로 승인되어 지원자가 팀원이 된다(투표할 팀원이 없음).
- 팀원이 있는 팀이면 대기가 된다.

### 4.3 투표
- 투표할 사람은 투표하는 때의 그 팀의 팀원 전원이다. 지원한 뒤에 다른 지원자가 먼저 승인되어 팀원이 되면, 그 사람도 투표한다.
- 한 명이라도 거부하면 다른 팀원의 투표를 기다리지 않고 바로 거절된다.
- 팀원 모두가 찬성하면, 승인하기 직전에 규칙(정원, 주 역할 중복, 필수 포함 역할 자리)을 그때의 팀 구성으로 다시 검사한다(공고 3장 어려운 해결). 통과하면 승인, 어기면 거절이다.
- 같은 팀에 대기 중인 지원이 여럿이면, 처리 순서는 지원한 순서가 아니라 투표가 끝난 순서이다. 그 전에는 대기 중인 지원을 미리 거절하지 않는다.
- 한 번 투표하면 바꿀 수 없다. 투표한 지원에는 그 학생의 찬성·거부 단추를 숨기고 "내 투표: 찬성"처럼 보여 준다.
- 이미 결과가 나온 지원에 투표 단추를 누르면(화면이 바뀌기 전 몇 초 사이), 그 지원의 지금 상태를 안내한다.

### 4.4 필수 포함 역할 자리 계산 (공고 3장 표 아래 설명)
지원(4.2절 6번)과 승인 직전 검사(4.3절)에서 같은 계산을 쓴다.

1. 지원자를 넣은 뒤의 팀원 목록을 만든다.
2. 기획자와 웹 프로그래머를 팀원 중 서로 다른 학생에게 맡길 때, 최대 몇 개를 채울 수 있는지 센다. 한 학생이 둘 다 맡을 수 있어도 하나로만 센다.
3. 못 채운 필수 역할 수 = 2 - (2에서 센 수).
4. 남는 자리 수 = 4 - (지원자를 넣은 뒤의 팀원 수).
5. 남는 자리 수 < 못 채운 필수 역할 수이면 막는다.

예:
- 주 역할이 기획자이고 보조 역할이 웹 프로그래머인 학생 혼자 있는 팀은 필수 역할 2개 가운데 1개만 채운 것이다.
- 테스터와 발표자만 있는 팀(2명)에 보고서 작성자가 지원하면, 남는 자리 1개로 필수 역할 2개를 채울 수 없으므로 막는다.

### 4.5 마감 (공고 2.5절)
관리자가 "모집 마감"을 누르면 한 번에 다음을 처리한다.
1. 마감 표시를 한다. 그 뒤로는 지원과 투표를 할 수 없다.
2. 대기 중인 지원을 모두 거절한다(사유: 모집 마감).
3. 1명뿐인 팀의 학생을 팀에서 빼서 "팀이 없는 학생"으로 만든다.

### 4.6 배정 (공고 2.5절)
1. 관리자가 "AI 배정"을 누르면, 앱은 먼저 규칙을 지키는 배정이 있는지 모든 경우를 따져 본다. 없으면 AI를 부르지 않고 `assign_status`에 "규칙을 지키는 배정이 없음"과 이유를 보여 준다(예: 팀3에 웹 프로그래머를 맡을 학생이 없음).
2. 있으면 AI(1차 모델)에게 지금의 팀 구성, 팀이 없는 학생과 역할, 규칙을 보내 배정안을 받는다.
3. 배정은 팀이 없는 학생만 팀에 넣는다. 이미 팀에 있는 학생은 옮기지 않는다.
4. 앱은 배정안을 다섯 가지로 검사한다.
   - 팀이 없는 학생이 빠짐없이 배정됨
   - 한 학생은 한 팀에만 배정됨
   - 모든 팀이 2~4명
   - 팀 안에서 주 역할 중복 없음
   - 필수 포함 역할 충족
5. AI가 응답하지 않거나(모델마다 전체 대기 시간 120초), 빈 응답·오류를 내거나, 배정안이 검사를 통과하지 못하면 2차 모델, 3차 모델 순으로 다시 배정한다.
6. 3차 모델까지 실패하면 앱이 모든 경우를 따져 검사 다섯 가지를 모두 통과하는 배정을 스스로 찾는다(공고 3장 어려운 해결).
7. 검사를 통과한 배정안만 관리자에게 보여 준다(학생의 이름과 역할, 배정된 팀). 관리자가 확정하면 DB에 저장한다.
8. 확정할 때는 배정안을 만든 뒤 상태가 바뀌지 않았는지 다시 검사한다.
9. 마감 뒤 팀이 없는 학생이 한 명도 없으면 AI를 부르지 않는다. 지금 팀이 모두 규칙(2~4명, 주 역할 중복 없음, 필수 포함 역할)을 지키면 빈 배정안을 만들어 "배정할 학생이 없어 지금 팀 구성을 그대로 확정할 수 있음"을 보여 주고, 관리자는 "배정안 확정"으로 지금 팀 구성을 그대로 확정한다(0명). 규칙을 어긴 팀이 있으면(예: 빈 팀) 1번처럼 `assign_status`에 "규칙을 지키는 배정이 없음: 이유"를 보여 준다.

## 5. 화면

### 5.1 공통
- 로그인 화면: 학번 입력칸, 비밀번호 입력칸(입력 글자 가림), 로그인 단추.
- 로그인한 뒤 맨 위에 로그인한 사람을 보여 준다(`whoami`).
  - 학생은 "로그인: 학생1(PL;RW) (2026101)", 관리자는 "로그인: 관리자 (admin)".
- 로그아웃 단추는 사이드바에 둔다.
- 결과 안내(`result`)는 단추를 누른 사람의 화면에 보인다. 문구는 승인·대기·거절·막힘 가운데 하나로 시작하며, 색은 승인 초록, 대기 파랑, 거절 노랑, 막힘 빨강이다(Streamlit의 success, info, warning, error 상자).
  - 결과 안내는 화면이 3초마다 다시 그려져도 다음 단추를 누를 때까지 남는다.
  - 아직 단추를 누르지 않았으면 "단추를 누르면 결과가 여기에 나옴"을 보여 준다.
- 명단을 다시 올려 로그인한 학생이 명단에서 사라지면, 그 학생의 화면은 로그인 화면으로 돌아간다.
- 다른 사람의 변경은 `st.fragment(run_every=3)`로 3초마다 저절로 다시 그린다(공고 3장 어려운 해결). 공고는 5초 이하 간격을 요구하고 채점 프로그램은 단추가 나타나기를 7초까지 기다리므로, 화면을 그리는 시간까지 넉넉히 들어가도록 3초로 정한다. 화면에 "화면은 3초마다 저절로 바뀜"이라고 적는다. 새로 고침 단추는 두지 않는다.
- 관리자 화면에서 자동으로 다시 그리는 부분은 현황(팀이 없는 학생 표시와 팀 카드)뿐이다. 자동 새로 고침은 실행 중인 화면을 끊지 않고 기다렸다가 실행되므로(Streamlit은 fragment의 run_every 요청을 대기열에 넣음), AI 배정이 몇 분 걸려도 중간에 끊기지 않는다.
- 화면에 보이는 시각은 한국 시간(UTC+9)으로 바꿔 보여 준다.

### 5.2 학생 화면 (위에서부터)
1. 상태 줄: "모집 상태: 모집 중 · 내 팀: 팀1 · 화면은 3초마다 저절로 바뀜". 팀이 없으면 내 팀 자리에 "아직 팀이 없음".
2. 내 팀에 들어온 지원 (팀이 있을 때만)
   - 대기 중인 지원마다 한 줄: 지원자 이름 · 학번 · 주 역할 · 보조 역할 · 지원 시각
   - 오른쪽에 찬성 단추와 거부 단추. 이미 투표했으면 단추 대신 "내 투표: 찬성"(또는 거부).
   - 대기 중인 지원이 없으면 "대기 중인 지원 없음".
3. 팀 목록
   - 팀마다 테두리 상자(팀 카드)를 옆으로 나란히 둔다.
   - 카드 제목은 "팀1 (2/4명)". 로그인한 학생의 팀이면 제목에 "내 팀"을 붙이고 상자를 진하게 표시한다.
   - 팀원마다 "학생1(PL;RW) · 주 역할 기획자 · 보조 역할 보고서 작성자". 팀원이 없으면 "빈 팀".
   - 카드마다 "팀N에 지원" 단추.
   - 이미 팀에 속했거나, 결과를 기다리는 지원이 있거나, 모집이 마감되었으면 지원 단추를 모두 비활성화하고, 팀 목록 위에 이유를 한 줄로 적는다(예: "지원 단추를 쓸 수 없음: 팀1에 낸 지원이 대기 중입니다").
   - 그 밖에 막히는 지원(팀이 꽉 참, 같은 주 역할, 필수 역할 자리)은 단추를 눌렀을 때 "막힘: 이유"로 안내한다.

### 5.3 관리자 화면 (위에서부터)
1. 명단 올리기
   - 설명: 명단 CSV(UTF-8, 머리글 `student_no,name,main_role,sub_roles`)와 팀 수를 넣고 단추를 누르면 지원·투표·팀원·마감 표시를 모두 지우고 처음 상태를 만든다.
   - 명단 CSV 올리기, 팀 수, "명단으로 처음 상태 만들기" 단추.
2. 마감과 배정
   - 모집 상태(모집 중/마감), "모집 마감" 단추.
   - 팀이 없는 학생 표시: "팀이 없는 학생 2명: 학생7(FD;PT), 학생8(TT;RW;PT)". 없으면 "팀이 없는 학생 0명: 없음".
   - "AI 배정" 단추.
   - AI 배정 진행 안내(`assign_status`)
     - 기다리는 동안: "1차 모델(모델 이름)의 응답을 기다리는 중... (최대 120초)"
     - 모델마다 결과 한 줄: "1차 모델(…): 시간 초과(120초) → 2차 모델로 넘어감", "2차 모델(…): 검사 통과 (16초)"
     - 3차까지 실패: "3차 모델까지 실패하여 앱이 직접 배정함"
     - 배정할 수 없을 때: "규칙을 지키는 배정이 없음: 이유"
   - 검사를 통과한 배정안 표(이름 · 주 역할 · 보조 역할 · 배정된 팀)와 출처(몇 차 모델 또는 앱), "배정안 확정" 단추.
     배정할 학생이 없는 빈 배정안(4.6절 9번)이면 표 대신 "배정할 학생이 없어 지금 팀 구성을 그대로 확정할 수 있음"을 적고 "배정안 확정" 단추를 둔다.
3. 현황
   - "학생 n명 · 팀이 없는 학생 n명 · 화면은 3초마다 저절로 바뀜"
   - 학생 화면과 같은 팀 카드로 팀 구성을 보여 준다.

## 7. 데이터

### 7.1 테이블 (공고 5장 최소 참고안 + 필요한 열)
모든 테이블 이름은 `tf_`로 시작한다(감점 13번).

| 테이블 | 열 | 제약 |
|---|---|---|
| `tf_students` | id, student_no, name, main_role, password_hash, is_admin | student_no 유일, main_role은 6개 역할 중 하나(관리자는 비움) |
| `tf_student_sub_roles` | student_id, role | (student_id, role) 기본 키, role은 6개 역할 중 하나 |
| `tf_teams` | id(팀 번호), name | name 유일 |
| `tf_members` | team_id, slot_no, student_id | (team_id, slot_no) 기본 키, student_id 유일, slot_no는 1~4 |
| `tf_applications` | id, team_id, student_id, status, reason, created_at, decided_at | status는 대기·승인·거절 중 하나, 학생마다 대기 중인 지원은 1개만(부분 유일 인덱스) |
| `tf_votes` | application_id, voter_id, vote, created_at | (application_id, voter_id) 기본 키, vote는 찬성·거부 중 하나 |
| `tf_settings` | key, value | key 기본 키. 마감 여부 저장 |

- `tf_members`의 (team_id, slot_no) 기본 키와 student_id 유일 제약이, 마지막 자리에 두 명이 동시에 들어갈 때 먼저 도착한 학생만 기록하고 한 학생이 한 팀에만 속하게 한다(공고 3장 어려운 해결).
- 모든 tf_ 테이블에 행 수준 보안(RLS)을 켜고 정책은 만들지 않는다. Supabase Data API(anon 키)로는 아무 행도 읽거나 쓸 수 없고, 앱은 DB 소유자 계정으로 직접 접속하므로 영향이 없다(비밀번호 해시 보호).
- 테이블을 만드는 SQL은 저장소의 `schema.sql`에 둔다. 앱은 시작할 때 이 파일을 실행해 테이블이 없으면 만든다(`create table if not exists`).

### 7.2 쓰기 처리
- 지원, 투표, 마감, 확정은 각각 하나의 트랜잭션으로 처리한다.
- 쓰기 처리(명단 올리기, 지원, 투표, 마감, 확정)는 트랜잭션을 시작하자마자 `pg_advisory_xact_lock`으로 잠가 한 번에 하나씩 처리한다. 잠근 뒤에 상태를 다시 읽고 규칙을 검사하므로, 두 학생이 같은 순간 지원하거나 마감과 지원이 겹쳐도 검사한 상태와 쓰는 상태가 같다. 잠금이 빠지더라도 7.1절의 유일성 제약이 마지막으로 막는다.
- 명단 올리기: 한 트랜잭션에서 관리자 계정을 뺀 학생, 지원, 투표, 팀원, 팀, 마감 표시를 지우고, 명단의 학생과 빈 팀을 만든다. 학생의 비밀번호 `1234`는 bcrypt 해시로 저장한다.

### 7.3 연결
- `DATABASE_URL`은 Supabase의 Session pooler 연결 문자열(IPv4 지원, 포트 5432)을 쓴다. Streamlit Community Cloud와 GitHub Actions는 IPv4로만 접속할 수 있어서 Direct connection(IPv6 전용)은 쓰지 않는다. Supabase 프로젝트 지역은 배포 서버와 가까운 East US(North Virginia)이다.
- DB 연결은 앱 프로세스에서 한 번만 만든 연결 풀(`st.cache_resource`)을 재사용한다. 질의마다 연결을 새로 만들지 않는다(공고 4.2절).
- 화면을 한 번 그릴 때 필요한 상태(학생, 팀, 팀원, 대기 지원, 투표, 마감 여부)는 한 번의 질의로 읽어 DB 왕복을 줄인다.
- 연결이 끊어졌으면 다시 연결한다.

## 8. AI 배정

### 8.1 모델
- 오픈라우터의 무료 텍스트 생성 모델 3개를 1차, 2차, 3차로 정한다. 이름이 `:free`로 끝나는 모델만 쓴다.
- 무료 모델로 자동 연결하는 openrouter의 free 라우터는 쓰지 않는다(감점 14번).
- 모델 이름은 코드의 상수 목록 한 곳에 두고 README 4항에 적는다.
- 후보(2026-10-24 기준 공개 목록에서 고름. 최종 선택은 과제 수행자가 함):
  - `google/gemma-4-31b-it:free` — 추론 모델이 아니라 빈 응답 위험이 적고, 구조화 출력을 지원함
  - `nvidia/nemotron-3-super-120b-a12b:free` — 시연 동영상의 시범 앱이 1차로 써서 검사를 통과한 모델
  - `poolside/laguna-s-2.1:free` — 최근 하루 가동률이 높음

### 8.2 요청
- 오픈라우터 Chat Completions API에 `OPENROUTER_API_KEY`로 요청한다.
- reasoning effort는 low, `max_tokens`는 넉넉히 준다(공고 4.3절, 빈 응답 줄이기).
- 보내는 내용: 규칙(4.1절), 팀마다 지금 팀원과 역할, 남는 자리, 팀이 없는 학생의 학번·주 역할·보조 역할.
- 받는 형식: JSON `{"assignments": [{"student_no": "2026107", "team": 1}, …]}`. 응답에 다른 글이 섞여 있어도 JSON 부분만 꺼내 읽는다.

### 8.3 실패 처리 (공고 3장 어려운 해결)
- 모델마다 요청을 시작한 때부터 전체 대기 시간을 재서 120초가 넘으면 끊고 다음 모델로 넘어간다. 응답이 천천히 오는 경우도 120초에 끊는다.
- 실패로 보는 경우: 시간 초과, HTTP 오류(429 포함), 빈 응답, JSON을 읽을 수 없음, 배정안이 검사 다섯 가지를 통과하지 못함.
- 모델마다 결과(성공·실패와 이유, 걸린 시간)를 `assign_status`에 한 줄씩 남긴다. 이 화면이 README 5항(AI 모델 호출 실패 사례)의 근거가 된다.
- 가장 오래 걸려도 120초 × 3 + 앱의 직접 배정이므로 10분 안에 끝난다(감점 18번).

### 8.4 앱의 직접 배정 (3차 모델까지 실패할 때, 그리고 4.6절 1번의 사전 검사)
- 팀이 없는 학생을 한 명씩 들어갈 수 있는 팀에 넣어 보며 모든 경우를 따진다(백트래킹).
- 정원, 주 역할 중복, 필수 역할 자리 계산(4.4절)으로 가망 없는 경우를 일찍 버린다. 비어 있는 팀끼리는 서로 바꿔도 같으므로 한 번만 따진다.
- 첫 번째로 찾은, 다섯 가지 검사를 모두 통과하는 배정을 쓴다.
- 배정이 없으면 이유를 찾아 보여 준다. 예: 남은 자리보다 팀이 없는 학생이 많음, 팀을 2명 이상으로 채울 학생이 모자람, 팀3에 웹 프로그래머를 맡을 학생이 없음, 웹 프로그래머를 맡을 학생이 모자람(필요 n명, 가능 m명).

### 8.5 호출 횟수
- 무료 모델은 계정마다 하루 50회, 분당 20회까지이다. 실패한 호출도 횟수에 들어간다.
- 채점 기간(11/3~11/4)에는 채점자가 이 키로 AI를 부르므로, 그 이틀 동안은 직접 AI 배정을 시험하지 않는다.
- 규칙 검사와 앱의 직접 배정은 AI 없이 자동 테스트로 확인해 호출 횟수를 아낀다.

## 9. 공고 3장 해결 방법 선택

| 기능 | 고른 해결 | 만드는 방법 |
|---|---|---|
| 다른 사람의 변경 보기 | 어려운 해결 | `st.fragment(run_every=3)`로 바뀐 부분만 3초마다 다시 그림 |
| 필수 포함 역할을 지킬 수 없는 팀 | 어려운 해결 | 지원 단계에서 필수 역할 자리 계산(4.4절)으로 막음 |
| 같은 팀에 대기 중인 지원이 여럿 | 어려운 해결 | 승인 직전 재검사, 투표가 끝난 순서로 처리 |
| 마지막 자리에 두 명이 동시에 들어감 | 어려운 해결 | `tf_members`의 유일성 제약 + 쓰기 직렬화 잠금(`pg_advisory_xact_lock`) |
| AI 응답이 늦을 때 | 어려운 해결 | 모델마다 120초 전체 대기 시간을 재서 끊고 다음 모델로 |
| 3차 모델까지 실패 | 어려운 해결 | 모든 경우를 따져 다섯 가지 검사를 통과하는 배정을 찾음 |
| AI 대기 중 화면 | 어려운 해결 | 몇 차 모델의 응답을 기다리는지 보여 줌 |
| DB(Supabase)가 일시정지되지 않게 | 어려운 해결 | GitHub Actions 예약 작업이 매일 DB에 질의를 보냄 |

## 10. 보안과 키 관리 (공고 4.1절, 감점 7·8·10·11·12번)
- `OPENROUTER_API_KEY`, `DATABASE_URL`, `ADMIN_PASSWORD`는 로컬에서는 `.env`, 배포한 앱에서는 Streamlit Secrets에만 둔다.
- `.gitignore`에 `.env`와 `.streamlit/secrets.toml`을 넣는다. 저장소에는 값이 빈 `.env.example`만 둔다.
- 코드는 키 값을 화면이나 로그에 출력하지 않는다. 키가 있는지 확인할 때는 "있음/없음"만 보여 준다.
- 오류가 나도 오류 원문(접속 주소가 섞일 수 있음)을 화면에 보여 주지 않고 일반 안내만 보여 준다. Streamlit의 오류 상세 표시도 끈다.
- 비밀번호는 bcrypt로 해시해 저장하고, 로그인할 때 입력한 비밀번호를 같은 방법으로 비교한다.
- 관리자 단추를 누를 때마다 로그인한 계정이 관리자인지 DB로 다시 확인한다. 학생 계정은 관리자 화면을 볼 수 없고 관리자 기능도 쓸 수 없다.
- 학번만으로는 로그인할 수 없고, 비밀번호가 틀리면 로그인되지 않는다.
- 명단 CSV, 코드, 문서, 화면 캡처에는 가상 학생만 쓴다. 실제 사람의 이름이나 학번을 쓰지 않는다(README 작성자 이름은 예외).

## 11. 배포와 운영 (공고 4.4절)
- 기술 구성: Python 3.13, Streamlit 1.66.0(버전 고정), psycopg2-binary(DB), bcrypt(비밀번호 해시), requests(오픈라우터 요청), python-dotenv(로컬 `.env` 읽기). 배포 설정의 Python 버전도 로컬과 같은 3.13으로 고른다.
- Streamlit Community Cloud에 배포한다. 저장소의 기본 브랜치(`main`)와 앱 파일 `streamlit_app.py`로 배포한다.
- 깃허브 저장소는 만드는 동안 비공개로 두고, Streamlit의 Linked accounts에서 비공개 저장소 접근을 허락한다. 배포한 앱은 "This app is public and searchable"로 바꾸고 로그인하지 않은 브라우저(시크릿 창)로 로그인 화면이 보이는지 확인한다.
- DB 일시정지 막기: `.github/workflows/keep-alive.yml`이 매일 한 번 DB에 간단한 질의를 보낸다. DB 주소는 깃허브 저장소의 암호화된 Actions Secrets에 넣는다(코드와 커밋 기록에는 남지 않음).
- 배포 서버의 시각은 UTC이므로, 화면에 보이는 시각은 한국 시간으로 바꾼다.
